# Auth Service — Навык дня

Отдельный сервис ASP.NET Core 10 + ASP.NET Core Identity + PostgreSQL. Отвечает за учётные записи, подтверждение email, вход, сессии и роли. Фронтенд подключён к реальному API; статистика вакансий и персональные настройки пока остаются демонстрационными.

Корневой `compose.yaml` запускает реализацию из этой папки с отдельной БД `auth-db` и миграциями EF Core. В `backend/Services/AuthService` также есть заготовка инфраструктуры с миграцией FluentMigrator; она не используется этим контейнером. Общий `backend/Migrator` и миграции этого сервиса работают независимо.

## Быстрый запуск

Из корня репозитория:

```sh
docker compose up -d --build
```

- Сайт: **http://127.0.0.1:8080**
- Локальные письма Mailpit: **http://127.0.0.1:8025**
- OpenAPI JSON: **http://127.0.0.1:8080/api/auth/openapi/v1.json** (Development)
- Публичный JWKS: **http://127.0.0.1:8080/api/auth/.well-known/jwks.json**

Зарегистрируйте почту с паролем от 12 до 128 символов, откройте письмо в Mailpit и подтвердите адрес по ссылке из письма. После этого можно войти. Используется локальный Mailpit: он принимает письма и не пересылает их внешним адресатам. Gmail и другие внешние SMTP-провайдеры не подключены.

`compose.yaml` — окружение локальной разработки: HTTP на loopback, PostgreSQL без опубликованного порта и SMTP из `.env`. В нём четыре контейнера: frontend, auth-service, auth-db, mailpit. При выборе Gmail Mailpit остаётся доступным для тестов, но письма приложения в него не попадают. PostgreSQL и ключи подписи сохраняются в отдельных именованных volumes; остановка и обычная пересборка данные не удаляют. Не удаляйте volumes, если хотите сохранить учётные записи и действующие сессии.

```sh
docker compose ps
docker compose logs -f auth-service
docker compose stop
```

Отдельного API Gateway пока нет. Nginx фронтенда отправляет `/api/auth/*` непосредственно в `auth-service:8080/auth/*`, снимая только `/api`. Остальные `/api/*` по-прежнему предназначены для будущего Gateway. Контракт Auth Service можно перенести на Gateway без изменения URL браузера.

## Контракт API

В таблице пути сервиса. Для строк `/auth/...` через сайт добавляется `/api`; `/health/...` доступны внутри Docker-сети. При импорте OpenAPI в API-клиент используйте базовый URL `http://127.0.0.1:8080/api`. Запросы с телом используют JSON; ошибки — Problem Details с `title`, иногда `code` или `errors`. Доступ проверяется через `Authorization: Bearer <accessToken>`.

| Метод и путь                      | Назначение                               | Доступ / результат                                        |
| --------------------------------- | ---------------------------------------- | --------------------------------------------------------- |
| `POST /auth/register`             | `{email,password}`; письмо подтверждения | `202`, одинаково для нового и существующего адреса        |
| `POST /auth/confirm-email`        | `{userId,code}` из письма                | `204`                                                     |
| `POST /auth/resend-confirmation`  | `{email}`                                | `202`, нейтральный ответ                                  |
| `POST /auth/login`                | `{email,password}`                       | `200`, JWT + пользователь; refresh устанавливается cookie |
| `POST /auth/refresh`              | Продление из cookie, без тела            | `200`; обязательный заголовок Origin                      |
| `POST /auth/logout`               | Завершить текущую сессию                 | `204`; Origin + cookie                                    |
| `POST /auth/logout-all`           | Завершить все сессии пользователя        | Bearer, `204`                                             |
| `GET /auth/me`                    | Текущая учётная запись и роли            | Bearer, `200`                                             |
| `POST /auth/forgot-password`      | `{email}`; письмо восстановления         | `202`, нейтральный ответ                                  |
| `POST /auth/reset-password`       | `{userId,code,newPassword}` из письма    | `204`, все сессии отозваны                                |
| `POST /auth/change-password`      | `{currentPassword,newPassword}`          | Bearer, `204`, все сессии отозваны                        |
| `POST /auth/change-email`         | `{newEmail,currentPassword}`             | Bearer, `202`; письмо на новый адрес                      |
| `POST /auth/confirm-email-change` | `{userId,newEmail,code}` из письма       | `204`, все сессии отозваны                                |
| `DELETE /auth/account`            | `{currentPassword}`                      | Bearer, `204`; удаление учётки и её сессий                |
| `GET /auth/admin/check`           | Проверка роли администратора             | Bearer + Admin, `204`; обычному пользователю `403`        |
| `GET /auth/.well-known/jwks.json` | Публичный ключ проверки JWT              | `200`, приватных параметров нет                           |
| `GET /health/live`                | Процесс работает                         | `200`                                                     |
| `GET /health/ready`               | Доступна БД                              | `200` / `503`                                             |

Ответ входа и продления:

```json
{
  "accessToken": "<JWT>",
  "tokenType": "Bearer",
  "expiresIn": 600,
  "user": {
    "id": "<UUID>",
    "email": "user@example.test",
    "emailConfirmed": true,
    "roles": ["User"]
  }
}
```

Неверные данные входа, неподтверждённая почта и временная блокировка дают одинаковый `401`. После пяти неверных попыток вход блокируется на 15 минут. Ограничение запросов: 100 в минуту на auth-endpoints, 20 на почтовые endpoints, глобально 200; `429` содержит `Retry-After`. Сейчас счётчик использует IP непосредственного соединения, поэтому посетители через один Nginx делят лимит. При подключении общего Gateway настройте доверенные прокси и передачу реального IP средствами ASP.NET Core, не доверяя произвольному клиентскому X-Forwarded-For.

## Сессии и ключи

Access JWT подписывается RS256, живёт 10 минут и содержит `sub`, `sid`, `jti`, роли, issuer, audience и временные ограничения. Другие API должны проверять подпись по JWKS, алгоритм, issuer `skill-day-auth`, audience `skill-day-api` и срок действия, затем свои права на ресурс. Токен не содержит пароля и email.

Refresh — случайный 256-битный токен в `skill-day.refresh`, HttpOnly + SameSite=Strict. В БД хранится только SHA-256-хеш. Продление заменяет токен в транзакции с блокировкой строки; повтор использованного токена отзывает всю его сессию. Абсолютный срок сессии — 30 дней, продления не сдвигают его. В Production cookie также всегда Secure; Development допускает локальный HTTP.

Auth Service на каждом защищённом запросе дополнительно проверяет сессию и security stamp в БД: выход, смена пароля/email и удаление прекращают доступ сразу. Будущие сервисы со статической проверкой JWT увидят отзыв не позднее истечения его срока; для немедленной проверки можно обращаться с тем же Bearer к `/auth/me`.

Это собственный first-party Auth API для закрытого приложения, а не OAuth/OIDC-провайдер: эндпоинтов authorization code, SSO и OAuth-discovery здесь нет. ASP.NET Core Identity управляет учётками и паролями; JWT выпускаются стандартной библиотекой Microsoft IdentityModel.

Фронтенд держит access token только в памяти, восстанавливает сессию через cookie, продлевает её перед истечением JWT и повторяет защищённый запрос после одного успешного refresh. Web Locks сериализует продления, вход и выход между вкладками в поддерживаемых браузерах. Токены и пароли не записываются в localStorage. Локальные демопараметры плана разделены по ID пользователя. При отсутствии Web Locks остаётся защита от параллельных refresh внутри одной вкладки; строгая серверная проверка повтора может потребовать нового входа при гонке нескольких вкладок.

Cookie-операции требуют Origin из настроек; запросы с чужим Origin или `Sec-Fetch-Site: cross-site` отклоняются. CORS по умолчанию не открыт. Для вызовов curl к refresh/logout передавайте `Origin: http://127.0.0.1:8080`.

## Почта

Письма попадают в PostgreSQL outbox в той же транзакции, что создание учётки. Тело с токеном зашифровано ASP.NET Data Protection. Фоновый обработчик отправляет через SMTP, повторяет временные ошибки с задержкой, использует `FOR UPDATE SKIP LOCKED`, очищает доставленный payload. Доставка имеет семантику at least once: при сбое между SMTP-отправкой и фиксацией возможен дубль письма. Токены действий действуют один час; смена пароля/email делает старые токены невалидными. Доставленные и неотправленные записи удаляются после двух суток. Истёкшие сессии удаляются фоновым обслуживанием вместе с refresh-хешами.

Compose передаёт параметры `SMTP_*` из локального `.env` в настройки `Smtp__Host`, `Smtp__Port`, `Smtp__Security`, `Smtp__Username`, `Smtp__Password`, `Smtp__From`, `Smtp__Name`. Внешний SMTP требует обязательного TLS (`StartTls` или `SslOnConnect`), учётных данных и настоящего адреса отправителя. Неполная или небезопасная конфигурация останавливает запуск с указанием поля. Незашифрованный локальный Mailpit допускается только в Development.

### Gmail (необязательное подключение в будущем)

Скопируйте `.env.example` в `.env`, если файла ещё нет; существующие настройки сохраните. Включите [двухэтапную аутентификацию и создайте пароль приложения Google](https://support.google.com/accounts/answer/185833?hl=ru) с названием «Навык дня». Обычный пароль аккаунта здесь не подходит. В `.env` укажите:

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_SECURITY=StartTls
SMTP_USERNAME=your-address@gmail.com
SMTP_PASSWORD=<16 символов пароля приложения без пробелов>
SMTP_FROM=your-address@gmail.com
SMTP_NAME=Навык дня
```

Используйте один и тот же Gmail-адрес в `SMTP_USERNAME` и `SMTP_FROM`. Параметры сервера и TLS — из [документации Google](https://developers.google.com/workspace/gmail/imap/imap-smtp). Файл `.env` исключён из Git; не добавляйте его в коммиты и не публикуйте вывод `docker compose config`, содержащий секреты.

Сначала проверьте подключение и авторизацию без отправки письма:

```sh
docker compose build auth-service
docker compose run --rm --no-deps auth-service --check-smtp
```

При успехе примените настройки к работающему сервису:

```sh
docker compose up -d auth-service
```

Обычный `restart` не подхватывает изменения окружения. Зарегистрируйте свой настоящий адрес на сайте, откройте письмо в почтовом ящике и подтвердите адрес. Для уже созданного неподтверждённого аккаунта используйте повторную отправку письма на странице входа. `PUBLIC_ORIGIN` определяет адрес ссылки в письме: локальный `http://127.0.0.1:8080` открывается на том же компьютере, а для опубликованного сайта нужен его публичный origin.

## Администратор

Регистрация всегда назначает только User, привилегии из JSON игнорируются. По умолчанию администраторов нет. Для первоначального создания укажите в локальном `.env`:

```dotenv
AUTH_ADMIN_EMAIL=admin@example.test
AUTH_ADMIN_PASSWORD=<свой уникальный пароль от 12 до 128 символов>
```

Затем `docker compose up -d auth-service`. Bootstrap создаёт подтверждённую учётку или назначает Admin существующей с этим адресом; пароль существующей учётки не меняет. После назначения удалите эти две переменные из `.env` и повторно пересоздайте сервис. `.env` исключён из Git. Сама админпанель управления вакансиями остаётся демонстрационной; её серверный API ещё не реализован.

## Разработка и миграции

Установленный .NET SDK 10 выбирается через корневой `global.json`.

```sh
dotnet restore auth-service/src/AuthService/AuthService.csproj
dotnet build auth-service/src/AuthService/AuthService.csproj
dotnet tool restore
dotnet ef migrations add NextChange --project auth-service/src/AuthService
```

Схема `auth` содержит таблицы Identity, Sessions, RefreshTokens, OutgoingMails и историю миграций. Локальный Compose автоматически применяет проверенные миграции при старте. Для отдельного запуска задайте `ConnectionStrings__AuthDb`, `Auth__KeyDirectory`, `Auth__PublicOrigin`, SMTP и окружение. БД по умолчанию не публикуется на хост; при разработке можно добавить локальный Compose override с портом БД. Ключи и пользовательские данные не входят в образ и Git.

Пароль БД из Compose передаётся отдельно через `Database__Password` и собирается через NpgsqlConnectionStringBuilder, поэтому символы вроде `;` в нём не превращаются в параметры подключения.

Для отдельного применения миграций существует режим `dotnet AuthService.dll --migrate`. Для Production используйте Compose override с `ASPNETCORE_ENVIRONMENT=Production`, уберите разрешённый dev-origin и задайте `Auth__AutoMigrate=false`, примените миграции перед запуском, используйте HTTPS-origin и собственные параметры подключения/SMTP. Образ работает от пользователя `app`. Файлы RSA и Data Protection хранятся в `Auth__KeyDirectory`; volume должен быть доступен этому пользователю. Текущий вариант рассчитан на один экземпляр сервиса с постоянными ключами; несколько реплик требуют общего управляемого хранилища ключей и распределённого ограничения запросов.

## Проверки

Проверка SMTP-настроек без доступа к сети и БД (нужны .NET SDK 10 и Node.js 22+):

```sh
dotnet build auth-service/src/AuthService/AuthService.csproj
node --test auth-service/tests/smtp.test.mjs
```

Интеграционные сценарии ниже запускайте только с локальным Mailpit: они используют синтетические адреса `@example.test`, которые не предназначены для настоящей доставки. Для отдельного локального окружения сохраните SMTP-параметры из `.env.example` в другом файле, например `.env.test`, и выполните `docker compose --env-file .env.test up -d --build`. Затем из корня репозитория:

```sh
node --test auth-service/tests/auth.test.mjs
```

Сценарии используют реальные PostgreSQL, SMTP и Nginx, создают только тестовые адреса `auth-test-<UUID>@example.test`. Проверяются подтверждение почты, подпись JWT, ограничения ролей, refresh/replay, выход со всех устройств, одноразовый сброс пароля, смена email/пароля, Origin и удаление. Для другого адреса задайте `AUTH_TEST_ORIGIN` и `MAILPIT_URL`.

Отдельная проверка сохранения данных и ключей после перезапуска (сама перезапускает локальный auth-service):

```sh
node auth-service/tests/persistence.mjs
```

Проверка лимита запросов запускается отдельно в свежем временном окне; она намеренно достигает `429`:

```sh
docker compose restart auth-service
node --test auth-service/tests/throttling.test.mjs
docker compose restart auth-service
```

Браузерная проверка реального входа и писем:

```sh
cd frontend
AUTH_INTEGRATION=1 PLAYWRIGHT_BASE_URL=http://127.0.0.1:8080 npm run test:e2e -- --grep 'Real auth-service'
```

Обычный `npm test` проверяет расчёты и интерфейс с изолированным Auth API; реальные интеграционные браузерные сценарии по умолчанию пропускаются.

## Границы сервиса

Направление, регионы, изученные навыки, вакансии, рекомендации и их обновление раз в пять дней относятся к другим сервисам. Здесь хранится только учётная запись и доступ. При удалении сейчас очищаются Auth DB и локальные параметры текущего устройства; каскад удаления данных будущего Profile Service нужно реализовать при его подключении. Отдельный Gateway и развёртывание на удалённом сервере в эту работу не входят.
